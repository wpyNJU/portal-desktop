# Being 云端语音服务

这里保存桌面与手机通话共用的 Python 语音服务源码，包含查询短标题、按主题提醒和统一语音输出控制。它是独立服务，不随 Electron 在用户电脑上启动。

**完整网页版交付**：[打包与部署](DEPLOYMENT.md) · [流程图与状态说明](FLOW.md) · [第三方字体许可](THIRD_PARTY_NOTICES.md)。在仓库根目录运行 `npm run package:voice-web`，生成 `out/being-voice-web.zip`；解压安装依赖后运行 `python serve.py` 即可提供页面和 WebSocket。

## 同一通话的输出控制

- `SpeechOutput` 统一管理豆包直接回复、查询过渡句和任务报告。同一时刻只允许一个输出来源；切换时先发送 `playback.clear` 清空客户端旧音频。
- 豆包的 PCM 增量不带回复编号，须按 `response.output_audio.started` 关联；即使旧回复已被屏蔽，也继续观察其开始/结束事件，避免迟到音频被误认成新回答。仅带用量的 `response.done` 与前面的音频结束事件关联。
- 工具交接时立即屏蔽该问题的模型语音及后续续答，由报告调度器负责过渡和结果。用户插话优先停播；旧报告的迟到音频、分段确认和清理动作不能影响新回答。
- 任务查询继续在后台运行。报告只在用户、回答生成、客户端播放都空闲时进入；已确认的播放位置保留，打断后等待空闲再询问是否继续。带 `generation` 的客户端播放回执可额外过滤旧回执；未升级客户端仍兼容已有播放协议。
- 桌面与手机客户端都携带播放轮次，并丢弃旧轮次的音频、分段标记与清空事件。语音识别缺少开始事件时，首个非空转写也会执行完整停播；重复开始、迟到的旧转写不会打断新问题。
- 分段是否播完由客户端音频时钟确认，不依赖 JavaScript 的结束回调是否及时执行。网关收到确认即保存游标；打断后保留 3 秒确认窗口，处理不同连接的到达顺序差异。旧播放尝试的确认不能推进重新播放的游标；未播完的段落仍从段首续读。

## 最近问题优先

- 当前用户输入与当前回答始终优先；两者结束、音频播完并经过空闲保护后，才从待播集合选择事项。
- 以任务的 `requested_at`（用户最近一次提出、追问、查看或要求续播的时间）从近到远排序。流式正文、进度与完成事件只更新 `updated`，不会让晚返回的旧查询插到前面。时间相同则保留稳定顺序；同一查询的过渡句先于其报告。
- 用户重提旧任务会更新其优先级，继续复用原任务。自动观察、自动续读不更新时间；新字段随 SQLite 保存，旧记录用创建时间初始化，不改正文和播放位置。
- 等待空闲的事项不提前占住播放锁，每次可播放时重新排序。旧长报告在已经确认播放的句子边界给更新的待播事项让位，后续自动从保存位置继续；用户插话仍立即打断，并在之后空闲时按优先级征询是否续播。
- 已过时的排队过渡句跳过；跳过过渡句不会取消后台查询。已经完整确认播完的报告不会因用户在最后停顿期间开口而再次询问续播。

## 查询标题与报告

- 豆包调用 `ask_agent` 时同时给出完整 `message`、简短 `title` 和过渡句。标题不需要额外模型请求。
- `TaskStore` 分开保存原请求和短标题；去重继续按原查询判断，复用时不覆盖原标题。旧数据库自动添加 `request` 列，保留原问题、正文和播放位置；旧标题按原问题缩短显示。
- 正文流式返回后，报告在空闲时说明主题，例如“刚才查的项目甲发布进度，有内容返回了”。打断后问“关于项目甲发布进度，刚才还没讲完，你还要继续听吗？”
- 续播、查询失败和部分结果也带上同一主题。查询有返回不等于外部业务任务已完成。

## 转交 Being 的上下文

- 豆包会话继续携带最近 24000 字通话历史，用于续聊、判断是否需要查询和补全指代。
- `ask_agent.message` 是可独立理解的当前需求，保留必要的对象、时间、条件、否定和授权边界，不复制整段历史或无关话题。指代不明确时先询问用户。
- `AgentBridge` 直接将该需求放入请求 `message`，不再拼接浏览器历史说明；场景标记、会话 ID、流式接收与任务保存保持原有规则。此前已经发送的历史记录不会被这项改动删除，客户端是否隐藏语音场景由客户端展示逻辑决定。

## 运行与配置

需要 Python 3.11 或更新版本。安装运行依赖：

```sh
python -m pip install -r services/voice-gateway/requirements.txt
```

旧入口保留现网数据目录 `/data/private/wpy/minicpm-voice`，可通过 `VOICE_DATA_DIR` 指定其他目录，凭据、资料、任务库和用量日志随之迁移到该路径。独立网页版的 `serve.py` 默认使用本目录下的 `data/`，支持 `--data-dir`，无需编辑源代码。

由部署环境提供以下私有文件，不要放入 Git：

- `doubao-api-key.txt`：豆包 API Key，仅服务器读取。
- `agent-url.txt`：可选的旧默认 Being streaming 链接，包含 token，仅供旧资料兼容使用；新安装不需要。每个新连接仍须提供自己的 Being 链接并通过验证。
- 运行时生成的 `agent-tasks.sqlite3`、`assistant-profile*.json` 和 `logs/`：查询结果、助手资料和用量数据，不属于源码。

准备数据目录、私有配置和日志目录后启动：

```sh
python services/voice-gateway/doubao_server.py
```

服务监听 `127.0.0.1:22601`，提供 `/health` 与 `/ws`。桌面使用 HTTPS 网关转发后的 `/pipeline/ws`；部署环境须提供 TLS、WebSocket 转发和适当的访问控制。此目录不包含现有反向代理，也不会自动替换线上进程。

`mobile/index.html` 和 `mobile/call.js` 保存手机网页源码，现网分别部署为 `call.html` 和 `call-assets/call.js`。两份现网字体与 OFL 许可随包提供；测试录音不打包。手机采集按设备实际采样率重采样为 16 kHz、每帧 20 ms，与桌面保持一致。更新 HTML 中脚本版本以避开旧缓存；通话中不要替换客户端脚本。

更新已有部署时先备份源码和 SQLite，等待通话及后台查询空闲，再重启语音服务。首次启动会迁移数据库；已有未完成任务由启动恢复逻辑处理。

## 验证

```sh
python services/voice-gateway/run_tests.py
```

十三个离线脚本只使用 Python 标准库、临时数据库和模拟音频/Agent。覆盖插话时缺失/重复/迟到识别事件、句末抢接与确认迟到、最新问题优先、排队后重排、句末让位与游标续读、优先级持久化，以及实际 HTTP 边界的请求正文与通话历史分离、真实协议中的无编号音频帧、输出互斥、旧回复过滤、标题与原请求分离、旧库迁移、多任务主题、重复查询、流式报告、断线续接、播放游标、部分失败和空闲调度。不会读取真实密钥、录音或调用付费接口。

客户端回归：`npx vitest run tests/voice-playback.test.ts tests/voice-mobile.test.ts tests/voice-call.test.ts tests/voice-service.test.ts tests/voice-capture.test.ts`。使用实际播放/采集代码与模拟设备时钟覆盖长队列中断、末尾回调延迟、旧回调隔离以及 16/44.1/48 kHz 输入。模拟测试不能代表真人麦克风的回声消除效果，也未新增本地语义打断模型。

上线前另以合成测试问题验证过豆包能在原工具调用中返回标题并保留完整查询条件，未调用真实 Agent；现场凭据、测试录音和部署备份没有纳入仓库。

2026-09-29 的输出修复另用真实豆包接口验证了连续两轮普通回复、工具交接后的旧音频过滤、报告中途插话和新回复播放；工具结果为合成测试数据，未请求真实 Agent。部署后健康检查与公网 WebSocket 鉴权通过，已有任务的正文及播放位置保持不变。这些测试没有录制真人麦克风，实际设备的回声与主观听感仍需通话确认。
